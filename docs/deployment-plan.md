# Deployment, install and DX

Confirmed by the user 2026-10-16 (all of section 10 as recommended; see Status). How each of the four ways people run Tern
is installed, configured, updated, backed up and removed, how contributors build and test
all four locally, and what has to be built to get there. Written on branch `roadmap/deploy`
(main 20c7c38e2). Background: `docs/architecture.md` (the trust split),
`docs/backend-plan.md` (3.2, 5, B3), `docs/desktop-client-plan.md` (stages 2, 10, 11, 12,
19; T13; 0.1 items 22-23), `docs/self-hosting.md`, `docs/engine-protocol-plan.md`.

The gateway's design (pairing, device tokens, admin scope, the methods the web client
needs) belongs to `docs/web-gateway-plan.md` (session `tern-web-ready`, not yet written).
This plan covers only how the gateway is packaged, deployed, configured and upgraded, and
lists what it needs from that plan (section 7).

## 0. Summary

| Scenario | Works today | Main blockers | First thing to build |
|---|---|---|---|
| 1. Desktop only | macOS zip, deb, rpm, snap and an unsigned Squirrel installer build in CI; nothing is released | C++ engine still the default; no DMG; `tern` not bundled; no CLI on PATH; auto-update disabled; no Windows engine | DMG and `tern` in the app once stage 2 lands; static update feed |
| 2. Self-hosted backend | `docker build` + `docker run` and a stub guide | No published image, no compose file, no health check binary in a distroless image, desktop can't connect yet (B1-C) | Compose file with Caddy, image build in CI, full guide |
| 3. Backend + web mail | Nothing | No `--detached` engine, no engine-owned secrets (stage 11), no `tern account add` (stage 12), no gateway | Packaging design only, until stage 11 and the gateway exist |
| 4. Hosted by us | Nothing | B2/B3 of the backend, signup verification, abuse handling, quotas; per-user engines are a separate product | Design only; backend changes after B3 |

Proposed order (section 9): backend compose and image (no dependencies), release workflow,
dev stack, then desktop packaging after stage 2 merges, update feed, headless packaging
after stage 11 and the gateway, hosted last.

## 2. Scenario 1: desktop only

### 2.1 What the user does

1. Downloads `Tern-<ver>-arm64.dmg` (or the Windows installer, the deb/rpm, the snap) from
   the GitHub release or the website.
2. Drags Tern to Applications and opens it. Gatekeeper accepts it (signed, notarised,
   stapled).
3. Onboarding adds an account. The engine is the bundled `mailsync-rs`, started by the app.
4. Optional: Tern > Install Command Line Tools links `tern` and `tern-mcp` onto PATH.
   Preferences > MCP runs `tern-mcp install` for Claude Desktop, Claude Code or Codex.
5. Updates arrive in the background and apply on restart.

Where it fails today:

| Step | Problem | Fix |
|---|---|---|
| 1 | No DMG, no GitHub release for the desktop; builds go to an S3 bucket by commit (`desktop-build-macos.yml:141-156`) | DMG target; release workflow (section 8.3) |
| 2 | Signing and notarisation skip without secrets; notarisation uses Apple ID + app password only (`build.js:361-368`) while the engine uses an API key | Add secrets (user); move the desktop to `notarytool` with the API key, like `engine-release.yml` |
| 3 | `core.sync.engine` defaults to `cpp` (`src/shared/mailsync-process.ts:170`) and the CI builds bundle only `mailsync-rs` | No public release before stage 10 deletes the C++ engine, or flip the default first (question Q1) |
| 3 | Windows ships no engine at all (`desktop-build-windows.yml:3-6`); the engine needs a named pipe and a DPAPI store | Out of this plan: engine work. Windows builds stay internal until then |
| 4 | `tern` is not bundled; `tern-mcp` is bundled by stage 2 (client-s2, unmerged); nothing on PATH on macOS or Windows; the deb/rpm `/usr/bin/ternmail` is the Electron app | Bundle `tern`; install command (2.3); deb/rpm symlinks |
| 4 | CLI and tern-mcp look for the snap profile under `~/snap/mailspring` (`apps/cli/src/discovery.rs:29`, `apps/mcp/src/config.rs:15`) | One-line fix each, after stage 1 lands in `apps/cli` |
| 4 | The CLI only works while the desktop runs: `serve` exits 141 when its parent goes (`apps/engine/src/serve.rs:13`) | Stage 11 (`--detached`, engine reuse). Until then `tern` says the desktop isn't running |
| 5 | Auto-update is off: `UPDATE_FEED_BASE_URL = ''` (`src/main/autoupdate-manager.ts:20-23`); the URL format left in place is Mailspring's update server protocol | Static feed (2.4) |

Also: `win32metadata.CompanyName: 'Foundry 376, LLC'` and the copyright string in
`build.js` (lines 28, 367) are Mailspring leftovers.

### 2.2 Signing and notarisation

| Platform | What is signed | How | Secrets |
|---|---|---|---|
| macOS | App, every helper, `mailsync-rs`, `tern`, `tern-mcp` (all inside the bundle, hardened runtime, child entitlements), the DMG | `osxSign` in `build.js`; `notarytool` with an App Store Connect API key; staple app and DMG | `APPLE_CODESIGN_P12`, `APPLE_CODESIGN_KEY_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_API_KEY_P8`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`, `APPLE_PROVISIONING_PROFILE_B64` |
| macOS, standalone binaries | `mailsync`, `tern`, `tern-mcp` in the tarballs | `apps/engine/packaging/macos/sign.sh` and `notarize.sh` (exist, used for `mailsync`) | same |
| Windows | `Tern.exe`, helpers, `TernSetup.exe`, nupkg contents | Azure Trusted Signing (exists), `verify-windows-signatures.js` | `AZURE_*` (exist) |
| Linux | release files | `SHA256SUMS` signed with a project key (minisign or GPG), and GitHub build provenance attestations; snap signed by the store | one signing key |
| Images | `tern-backend`, `tern-headless` | `cosign` keyless (GitHub OIDC) and build provenance | none beyond `GITHUB_TOKEN` |

The keychain argument from desktop-client-plan section 5 applies: keychain items the engine
creates stay readable across updates only while every release is signed with the same
Developer ID. Unsigned dev builds use the file store.

### 2.3 CLI and tern-mcp on PATH

- macOS: Tern > Install Command Line Tools (and Preferences > General) creates
  `/usr/local/bin/tern` and `/usr/local/bin/tern-mcp` as symlinks into
  `Tern.app/Contents/Resources/app.asar.unpacked/`, asking for an admin password through
  `osascript` the way VS Code does. Offered once after the first account is added.
  Uninstall removes the links if they still point into the bundle.
- Linux deb/rpm: the packages create `/usr/bin/tern` and `/usr/bin/tern-mcp` symlinks next
  to `/usr/bin/ternmail`. Check for a name clash with existing distro packages that ship a
  `tern` binary before choosing the name (`node-tern` on Debian is the likely one).
- snap: `tern.cli` and `tern.mcp` apps (`snap alias` if the user wants plain names).
- Windows: added to the user PATH by the installer, when Windows has an engine.
- `tern-mcp install` already writes the absolute path into the MCP client config, so MCP
  works without PATH. After an app move or update the desktop rewrites a stale entry
  (stage 2).

### 2.4 Updates

The desktop has `autoupdate-manager.ts` with Electron's `autoUpdater` on macOS, Squirrel on
Windows and nothing on Linux. Replace the feed with static files on the GitHub release, so
there is no update server to run:

- macOS: `autoUpdater.setFeedURL({url, serverType: 'json'})` pointing at
  `https://github.com/ternmail/ternmail/releases/latest/download/update-<channel>-darwin-<arch>.json`
  (Squirrel.Mac's static JSON format: `currentRelease` and a `releases` list with the zip
  URL). The release workflow writes it.
- Windows: Squirrel reads `RELEASES` and the nupkg from
  `https://github.com/ternmail/ternmail/releases/latest/download/`.
- Linux: no in-app install. The app checks the same JSON file and shows "Tern <ver> is
  available" with a link; the package manager (or snap refresh) does the update. An apt and
  dnf repository can come later.
- Channels: `stable` and `beta`, chosen in Preferences (`core.updates.channel`). Beta builds
  are GitHub prereleases; `releases/latest` skips them, so the beta feed file is uploaded to
  a fixed `channel-beta` release that the workflow overwrites.
- The feed host is a build-time setting (`TERN_UPDATE_FEED`), empty in dev builds and forks,
  so a fork never updates from ours.
- Engine skew: the engine, `tern` and `tern-mcp` are inside the bundle, so they update with
  the app. Once stage 11 lets an engine outlive the app, the app compares the running
  engine's `build` and `protocol` and restarts it (stage 11, already planned).

### 2.5 First run and onboarding

Owned by stages 10 and 12 (engine started at launch with zero accounts, onboarding through
the engine). Deployment adds only the one-time prompt for command line tools, and, when a
Mailspring profile exists, the existing profile import (engine-port-status "Before
shipping").

### 2.6 Logs, health, uninstall

- Logs: `<profile>/engine.log`, `mailsync-<accountId>.log`, the Electron log. Help > Open Logs
  and `tern logs` (exists). A "Copy diagnostics" item collects versions, `engine.status` and
  the last log lines with secrets stripped.
- Health: `tern status` (exists) answers whether the engine runs and each account's state.
- Uninstall: dragging the app to the Bin leaves the profile, the keychain item ("Tern Engine"
  and "Tern Safe Storage"), MCP client entries and the PATH links. Add Preferences >
  Advanced > "Remove Tern from this computer…" that runs `tern-mcp uninstall` for every
  client, removes the links, the keychain items and, if asked, the profile, then quits.
  Document the manual steps. deb/rpm `postrm` removes the symlinks; the profile stays, as
  distro convention expects.

## 3. Scenario 2: self-hosted backend

### 3.1 What the user does

1. Has a Linux box with Docker and a DNS name (`tern.example.com`) pointing at it.
2. `curl -LO https://github.com/ternmail/ternmail/releases/latest/download/tern-backend-compose.tar.gz`,
   untars `deploy/backend/`, copies `.env.example` to `.env`, sets `TERN_DOMAIN`.
3. `docker compose up -d`. Caddy gets a certificate; the backend migrates its database and
   starts; its log says there are no users and how to add one.
4. `docker compose exec backend tern-backend user add you@example.com` prints a password.
5. In the desktop, Preferences > Tern Server, enters `https://tern.example.com`, signs in in
   the login window. Repeats on each device.

Without Docker: the musl tarball, a `tern` system user, `deploy/systemd/tern-backend.service`
and the existing Caddy or nginx snippets.

Where it fails today:

| Step | Problem | Fix |
|---|---|---|
| 2 | No compose file, no published image; the user builds from source | `deploy/backend/`, image on ghcr (needs the user's go-ahead to publish) |
| 3 | Distroless has no shell or curl, so a compose `healthcheck` can't call `/ping` | `tern-backend healthcheck` subcommand (GET `/ping` on the bind address, exit 0/1) |
| 3 | Nothing tells a new admin to create a user | Log a hint at startup when the users table is empty |
| 3 | `trusted_proxies` defaults to loopback, so behind Caddy in compose every login shares the proxy's rate-limit budget | Compose sets `TERN_TRUSTED_PROXIES` to the compose network's subnet, fixed in the compose file |
| 5 | The desktop has no server pane, login window or token handling (B1-C, waiting for `apps/desktop`) | B1-C, not this plan. Until then the backend serves only the harness |
| 5 | Tracking and sharing need B2 | B2-T, B2-S |

### 3.2 Compose file

`deploy/backend/compose.yaml`: two services.

- `backend`: `ghcr.io/ternmail/tern-backend:${TERN_VERSION}`, volume `tern-data:/data`,
  `TERN_PUBLIC_URL=https://${TERN_DOMAIN}`, `TERN_TRUSTED_PROXIES` set to the network's
  subnet, `read_only: true`, `cap_drop: [ALL]`, `no-new-privileges`, healthcheck
  `tern-backend healthcheck`, no published port.
- `caddy`: `caddy:2` (Apache-2.0), ports 80/443, the Caddyfile with `flush_interval -1`,
  volumes for its data and config.
- A `.env.example` with `TERN_DOMAIN`, `TERN_VERSION` (pinned, not `latest`), optional
  `TERN_SIGNUP`.
- A `compose.override.example.yaml` for people with their own proxy: drops Caddy, publishes
  `127.0.0.1:5101`.

The image is pinned by version in `.env`, so `docker compose pull` never upgrades by
surprise.

### 3.3 Config and secrets

The backend holds no secrets of its own beyond the database (password and token hashes). All
config is env or `tern.toml` (exists). No signing keys, no SMTP until scenario 4 needs it.

### 3.4 TLS and reverse proxy

Caddy in the compose file by default; the nginx and Caddy snippets in `docs/self-hosting.md`
for everyone else. The backend refuses a non-https public URL on a non-loopback host
(exists).

### 3.5 Backups and restore

- `tern-backend backup <path>` exists (`VACUUM INTO`, new server id). Add a scheduled
  backup inside `serve`: `[backup] dir`, `interval` (default off), `keep` (count), writing
  `tern-<timestamp>.db` 0600. Distroless has no cron, and a sidecar running the same image
  as a loop is more moving parts than about 80 lines of Rust (question Q8).
- Compose mounts `./backups:/backups` and sets `TERN_BACKUP_DIR=/backups`,
  `TERN_BACKUP_INTERVAL=24h`, `TERN_BACKUP_KEEP=14`. The user copies `./backups` off the box.
- Restore: `docker compose stop backend`, `docker compose run --rm backend restore
  /backups/<file>` (new: checks the file, removes leftover `-wal`/`-shm`, new server id;
  refuses while the server holds its data-dir lock), start. Clients re-sync from the new
  server id.
- From B2 the data dir also holds `assets/`; backups then need the asset tree. `backup`
  should write a directory (db + hard-linked or copied assets) once assets exist.

### 3.6 Upgrades and migrations

- `serve` already applies pending migrations at open (`repo/sqlite.rs:40-49`) and refuses a
  database newer than itself (`sqlite.rs:593` test). Add: take a backup to
  `<data_dir>/pre-migrate-<from>-<to>.db` before applying any migration, so a bad upgrade
  can be rolled back by restoring it with the old image.
- Upgrade: change `TERN_VERSION`, `docker compose pull && docker compose up -d`. Release
  notes say when a migration runs and whether downgrade needs the pre-migrate copy.

### 3.7 Version skew

| Pair | Rule |
|---|---|
| Desktop/engine to backend, metadata protocol | Mailspring-compatible paths and bodies; additive only. Already stable. |
| Desktop to `/tern/v1/*` | Additive within `v1`. A breaking change is `/tern/v2`, served beside `v1` for at least one release. |
| Features | The client gates on `features` from `/tern/v1/server` and `/tern/v1/me` (exists), never on the version string. A newer desktop against an older backend shows the feature as unavailable on this server. |
| Backend older than its database | Refuses to start (exists). |

`/tern/v1/server` reports `apiVersion: 1` (done), so a future breaking change can tell old
desktops to update instead of failing oddly.

### 3.8 Health and logs

- `GET /ping` (exists); `tern-backend healthcheck` for containers.
- Logs: tracing to stderr (exists). Add `TERN_LOG_FORMAT=json` for people who ship logs.
  Access logs drop paths under `/t/` (backend-plan 5, B3).
- A `GET /tern/v1/server` check from the desktop pane doubles as an external health check.

### 3.9 Uninstall

`docker compose down`, then `docker volume rm` for the data. The guide says what breaks:
tracking pixels and rewritten links in already-sent mail, shared pages, signature images
hosted on the server. Desktops keep working on `LocalOnly`; signing out first revokes their
tokens.

## 4. Scenario 3: self-hosted backend plus web mail

### 4.1 Shape

One compose file, four services, two images:

```
                    ┌──────────── caddy (TLS) ────────────┐
   tern.example.com │                                      │ mail.example.com
                    ▼                                      ▼
              tern-backend                     tern-gateway ── static apps/web
                                                    │ unix socket, same uid
                                                    ▼  (shared profile volume)
                                              mailsync --mode serve --detached
                                                      profile volume: run/engine.json,
                                                      accounts.json, secrets.enc, edgehill.db,
                                                      gateway/ (devices.json, control.sock)
```

- `engine` and `gateway` run the same `tern-headless` image with different commands, as
  the same non-root uid, sharing the whole profile volume with `TERN_CONFIG_DIR` set to it
  in both. The gateway finds the engine through `<config>/run/engine.json` and keeps its own
  state in `<config>/gateway/` (web-gateway-plan 2.7). The engine's peer-uid check (S6) then
  passes for the gateway and for `docker compose exec engine tern …`; Docker without user
  namespace remapping reports the same uid on both sides.
- The gateway serves the built `apps/web` from the image (`TERN_GATEWAY_WEB_ROOT`), so web
  and gateway always match in version and the web client talks to its gateway same-origin.
- The backend stays its own image and service, unchanged from scenario 2.
- No orchestrator: compose restarts crashed services; on bare metal, systemd units
  (`tern-engine.service`, `tern-gateway.service` with `BindsTo=`), which is what
  architecture.md and stage 19 already assume.

### 4.2 What the user does

1. Same as scenario 2, steps 1-2, with `deploy/server/` and both `TERN_DOMAIN` and
   `TERN_MAIL_DOMAIN` in `.env`.
2. `docker compose run --rm engine tern-setup` once: writes the engine key file to
   `./secrets/engine.key` (0600) and prints next steps. Or the user runs
   `openssl rand -base64 32 > secrets/engine.key`.
3. `docker compose up -d`.
4. Adds mail accounts: `docker compose exec engine tern account add` (IMAP prompt, or OAuth
   with a URL to open on any machine and a code to paste back). Or pairs a browser with the
   admin scope and adds accounts from the web.
5. `docker compose exec gateway tern-gateway pair --admin` prints a one-time code or link
   (the command reaches the running gateway over `<config>/gateway/control.sock`); the user
   opens `https://mail.example.com` and enters it. `tern-gateway devices list|revoke|rename`
   manage paired browsers.
6. Nothing for the backend in the browser: the engine holds the backend connection and
   token, and the web client never calls the backend in v1 (web-gateway-plan G8).

### 4.3 Dependencies (none of this works until they land)

| Need | Owner |
|---|---|
| `serve --detached` (no parent channel, no exit 141), migrate at startup, autostart of registered accounts, restart policy | desktop-client stage 11 |
| SecretStore file fallback keyed from `$CREDENTIALS_DIRECTORY` or `TERN_ENGINE_KEY_FILE` | stage 11 |
| `tern account add` with IMAP and OAuth (OAuth from a headless box needs a device-style or paste-the-redirect flow) | stage 12 |
| `apps/gateway` (`tern-gateway`): HTTP, pairing and cookies exist on roadmap/web-ready; the engine relay waits for desktop-client stage 1 | web-gateway plan |
| Engine methods the web client needs (query, files, drafts) | desktop-client stages 7, 9, 13, 16 |

### 4.4 Config and secrets on a headless box

- Engine key: a Docker secret (`secrets: engine_key: file: ./secrets/engine.key`) mounted at
  `/run/secrets/engine_key`, passed as `TERN_ENGINE_KEY_FILE`. Under systemd,
  `LoadCredential=engine.key:/etc/tern/engine.key` (or `LoadCredentialEncrypted=` with
  `systemd-creds`) and `$CREDENTIALS_DIRECTORY`, which stage 11 already reads.
- The key sits on the same disk as `secrets.enc` unless the user stores it elsewhere. The
  guide says so plainly (desktop-client-plan 0.1 item 15).
- Gateway: token hashes in `<config>/gateway/devices.json` on the shared profile volume. Env:
  `TERN_CONFIG_DIR`, `TERN_GATEWAY_BIND` (`0.0.0.0:5180` in the container),
  `TERN_GATEWAY_PUBLIC_URL` (required off loopback), `TERN_GATEWAY_WEB_ROOT`,
  `TERN_TRUSTED_PROXIES`; `TERN_GATEWAY_INSECURE_PUBLIC_URL=true` only for plain http off
  loopback.
- Integration API keys go through `secrets.set` (stage 12), not env.

### 4.5 TLS, exposure and proxies

- Two hostnames: `tern.example.com` (backend, must be public so recipients load pixels,
  redirects and shares) and `mail.example.com` (gateway). The gateway does not have to be
  public; the guide shows a Tailscale or WireGuard-only variant where Caddy binds the
  gateway site to the VPN interface.
- The browser never calls the backend (the engine does), so the backend's CORS layer stays
  as it is. A VPN-only gateway still needs an https name (`tailscale cert`, or a DNS name
  with a DNS-01 certificate); over plain http its session cookie loses `Secure`.
- The WebSocket needs `flush_interval -1` and long read timeouts, as the backend stream does.

### 4.6 Backups and restore

- Engine data that can't be rebuilt from the mail server: `accounts.json`, `secrets.enc`
  and the key, `settings.json`, `mcp.json`, local drafts, send-later and other local
  metadata in `edgehill.db`. Bodies and the rest of `edgehill.db` can be re-synced but take
  hours.
- Add `tern engine backup <dir>`: SQLite online backup of `edgehill.db` plus copies of the
  JSON files and `secrets.enc` (never the key), 0600. The scheduled backup option mirrors
  the backend's (`[backup]` in the engine's settings, or the same env names).
- Restore: stop the engine, put the files back, start. The key must be the same one.
- Gateway: device tokens; losing them means re-pairing, so it is optional to back up.

### 4.7 Upgrades and version skew

- Engine, gateway, web and CLI are one image and one version: no skew inside the box.
- The engine migrates its database at startup (stage 11). Take a pre-migration copy as the
  backend does.
- Desktop and headless engine syncing the same accounts are two engines acting on the same
  expirations. Without the backend's claims (backend-plan 3.8, stage 17) a scheduled send
  or reminder fires twice. The guide tells people running both to connect both engines to
  the backend; the engine should warn when it detects an expiration it executed was also
  executed elsewhere (open item for stage 17).
- Gateway protocol to web: same image, so no skew. Gateway to engine: `hello.protocol`
  (exists).

### 4.8 Health, logs, uninstall

- Engine: `tern status --json` as the container healthcheck (exits non-zero when the engine
  is unreachable); account states in the output.
- Gateway: `tern-gateway healthcheck` and `GET /healthz` (exist on roadmap/web-ready). It
  doesn't report on the engine, so a stopped engine doesn't mark the gateway unhealthy; the
  engine's own healthcheck covers that.
- Logs: engine files under the data volume plus stderr; gateway stderr.
- Uninstall: as scenario 2, plus a reminder that OAuth grants stay on Google and Microsoft
  until revoked (`account.remove {revoke: true}` does it per account).

## 5. Systemd and launchd units (scenarios 2 and 3 without Docker)

Shipped in the tarballs under `deploy/`:

- `tern-backend.service`: `DynamicUser=yes`, `StateDirectory=tern-backend`,
  `ProtectSystem=strict`, `NoNewPrivileges`, `Restart=on-failure`.
- `tern-engine.service` and `tern-gateway.service` (system or `--user`), with
  `LoadCredential` for the engine key and `RuntimeDirectory=tern` for the socket.
- `com.ternmail.engine.plist` for a Mac mini used as a server.

`tern service install` and `tern engine install` (stage 19, `apps/cli/src/service.rs`)
generate per-user units instead: a LaunchAgent or a systemd `--user` unit with the
profile's absolute paths, the bundled engine and a service binary copied into the profile,
which a static template can't carry. The templates here stay for server installs (system
units, `DynamicUser`, `LoadCredential`), and should match the generated engine unit's command
(`mailsync --mode serve --detached`, `CONFIG_DIR_PATH`, restart on failure only).

## 6. Scenario 4: hosted by us

Two products with different trust stories; the second is optional and separate.

### 6.1 Hosted backend

The same `tern-backend` image, run by us, signup open. Users sign in from the desktop
exactly as in scenario 2 with our URL prefilled as one choice.

What has to change in the backend first (after B2/B3):

| Need | Why | Size |
|---|---|---|
| Email verification and password reset | Open signup with no verification gets abused; hosted users forget passwords. Needs outbound SMTP for the backend's own mail (a transactional provider), never users' mail | M |
| Bot protection on signup and login (Turnstile or similar, off by default in the image) | Rate limits are per IP and email; signup floods need more | S |
| Quotas per user: tracked messages per day, share storage, asset count | Sharing and tracking are free hosting for phishing and malware without limits | S (B2-S has quotas; make them per plan) |
| Separate user-content host (`u.tern…` for shares, pixels, redirects) from the API and login host | Uploaded HTML must never share an origin with the login page; also lets the content host sit behind a CDN and be blocked separately | S (config: `content_url` next to `public_url`) |
| Abuse handling: report link on shared pages, `tern-backend share revoke <slug>`, `user disable` (exists), a blocklist of redirect targets | Takedown requests need tooling on day one | S |
| Postgres behind the `Repo` trait | Only when one SQLite file is the bottleneck. One process with SQLite handles a lot of users with this write pattern; measure first (O4) | L, later |
| Horizontal scaling of the stream fan-out | Same; in-memory watch per process (3.2) | L, later |

**Tenant isolation.** Per-row `user_id` in every table (exists), every query scoped by the
authenticated user, tracking rows found inside the sender's `ns` (backend-plan 5). Add a
test suite that runs every endpoint as user B against user A's ids.

**What we can and can't see.** We can see: account emails and names, device names and last
use, which mail accounts exist (8-hex ids, not addresses), plugin metadata (snooze times,
reminder settings, tracking ids, the recipient addresses inside tracking metadata, open and
click times), shared threads and pages (public by design), signature images, and request
IPs at the proxy (not stored by the backend). We can't see: mail credentials, mail bodies,
subjects, folders or contacts, because none of it is ever sent. The privacy policy lists
exactly this, and the desktop's server pane links to it.

**Billing hooks.** D2 says every feature works with no server, so there is nothing to
unlock in the desktop and no upgrade prompts there. Billing applies only to the hosted
service's limits. Keep it out of the backend: a separate billing service (Stripe webhooks)
sets a per-user `plan` through an admin API or `tern-backend user set-plan`, and the
backend enforces the quota table for that plan and reports limits in `/tern/v1/me`. A
self-hoster's backend has no plans and no limits beyond the safety caps.

**Operations.** One region, one VM or container, Caddy, scheduled backups to object storage,
uptime check on `/ping`, logs without `/t/` paths. Status page. A runbook for restore
(server id rotation makes clients re-sync).

### 6.2 Hosted mail access (per-user engine)

Not part of the backend, per architecture.md. If offered:

- One `tern-headless` deployment per user (engine + gateway), on an isolated runtime
  (Firecracker microVMs such as Fly Machines, or gVisor), its own volume, its own engine
  key, no network path to other tenants or to the backend's database.
- **What we could see.** We would run the process that holds the user's credentials and
  mail. Encryption at rest with a per-user key wrapped by a KMS limits what a disk or backup
  leak exposes and lets us audit key use, but the operator can still read mail while the
  engine runs. A key only the user holds (unlocked from the browser) would stop unattended
  sync after every restart, which defeats the always-on point. The honest framing: hosted
  mail access is "trust Tern like you trust your mail provider"; self-hosting (scenario 3)
  is the option for people who don't.
- **Cost, rough and to measure.** An idle engine with a few accounts is tens to a couple of
  hundred MB of RAM; the mail database with bodies and search is 1-10 GB per user. Storage
  and always-on memory dominate: on the order of $2-6 per user per month on Fly-style
  pricing, more with large mailboxes. Machines that suspend when idle cut memory cost but
  stop IDLE push, so new-mail latency becomes polling latency.
- **Signup and abuse.** A hosted engine sends mail from users' own accounts; abuse lands on
  their providers, but we'd need per-user send rate limits in the engine and a way to stop a
  tenant.
- Recommendation: don't build it until the hosted backend has run for a while and
  scenario 3 works; decide then (question Q7).

## 7. Agreed with the gateway plan

Settled with `tern-web-ready` on 2026-10-16 (`docs/web-gateway-plan.md` 2.7, on
roadmap/web-ready):

1. `tern-gateway` (`apps/gateway`) ships inside `tern-headless`; engine and gateway are two

6. The browser never calls the backend in v1, so no `TERN_WEB_ORIGINS`.

The engine service in the image still waits for stage 11; the gateway runs today against a
desktop-owned engine.

## 8. Developer experience

### 8.1 One-command setup

A root `Makefile` (no extra tool to install on macOS or Linux) with thin targets that call

### 8.5 Reproducible builds

- Rust: `--locked`, pinned toolchain (exists), `SOURCE_DATE_EPOCH` from the tag's commit,
  `--remap-path-prefix` for the home and workspace dirs, the Linux release built in a pinned
  image digest. CI builds the Linux binaries twice and compares hashes.
- Images: base images pinned by digest, `SOURCE_DATE_EPOCH` and `rewrite-timestamp` in
  BuildKit.
- Desktop: `npm ci` from the lockfile and a pinned Electron; asar and zip timestamps make

- Notices: `third-party-notices.sh` (exists) for every artefact; images keep `SOURCE.txt`
