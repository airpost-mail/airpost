# Desktop data layer: what it holds and what replaces it

Scope: `apps/desktop/src/data` (stores, models, query, database, drafts, attributes, tasks), `src/engine` (client, protocol, supervisor), `src/mail`. 155 files, 32.6k lines. Read-only survey, 2026-10-23.

Verdicts: **engine** (logic moves into the engine, the TS goes), **client** (stays in the desktop: rendering, layout, OS, window state, own prefs), **split** (UI part stays, domain part moves or comes from the shared TS client), **delete** (dead, or a fallback for an engine older than the one the desktop bundles).

"Shared client" below = the proposed `packages/` TS client used by desktop and web: generated protocol types, transport (Unix socket / WS), query + subscription client, model helpers.

## 1. How data reaches the UI today

Reads. `DatabaseStore` (src/data/database/store.ts, 614 lines) opens `airpost.db` read-only with better-sqlite3 in every window (WAL, 500-entry prepared-statement LRU, retry on "database is locked"/"schema has changed"). `.background()` queries go to a utility process (`database/agent.js`, spawned by `main/ipc/database-agent.ts`, port over MessagePort, exits after 5 s idle). Every query is a `ModelQuery` (`data/query/query.ts`) that compiles itself to SQL with `sql()` using the attribute classes in `data/attributes/*` (subselect on `ThreadCategory` for thread lists, `LEFT OUTER JOIN` for joined data like `MessageBody`).

The engine route already exists: with `core.engine.reads = "engine"` (default **"sqlite"**, src/config/schema.ts:30) `DatabaseStore._inflated` sends `ModelQuery.toJSON()` to the engine method `query` (crates/airpost-store/src/model_query.rs, 1388 lines; allowlist `model_query_allowlist.json` generated by `tests/integration/model-query-capture.test.ts`; parity test `crates/airpost-store/tests/model_query_parity.rs` runs the 65 captured call-site queries through both compilers). `EngineReads` (database/engine-reads.ts) waits up to 10 s for a hello, retries 3 times, emits `resync` after a reconnect. Only `structuredSearch()` can't be expressed as JSON (`toJSON()` throws), so search always stays on SQLite, although the engine already has `search.grammar: true` (`search_grammar.rs`, parity test `search_grammar_parity.rs`). The only raw SQL outside the query builder: `ThreadCountsStore._onCountsChanged` runs `SELECT * FROM ThreadCounts` when the engine lacks `counts`.

Changes. Every window opens its own Unix-socket connection (`engine/client/connection.ts`, Node `net` in the renderer) and calls `subscribe {accounts, classes: null}`: all classes, all accounts. Path of one change:

1. engine flushes a transaction -> `delta` notification `{type: persist|unpersist, modelClass, modelJSONs}` with whole model JSON;
2. `EngineConnection` 'deltas' -> `applyDeltas` (engine/client/bridge.ts) -> `Utils.convertToModel` per object (class registry) -> `new DatabaseChangeRecord` -> `DatabaseStore.trigger(record)`; side branches: `ProcessState` -> `OnlineStatusStore`, `ThreadCounts` -> `EngineEvents.threadCounts` -> `ThreadCountsStore`, persisted complete `Task` -> `task.onSuccess/onError` (main window only);
3. `QuerySubscriptionPool._onChange` hands the record to every live `QuerySubscription`; each one filters by class, runs `Model.matches(matchers)` = `Matcher.evaluate()` in JS (data/attributes/matcher.ts), checks if a sort key changed, and either patches its `MutableQueryResultSet` or refetches (ids-only range query, then `findAll({id: missing})`);
4. 19 other `DatabaseStore.listen` consumers do their own filtering: MessageStore, DraftStore, FocusedContentStore, ThreadCountsStore (fallback), MessageBodyProcessor cache, list selection (components/list/selection.ts), draft-list, main-calendar (x2), events (x2), unread-notifications (x2), SyncbackEventTask, plugins send-later, send-reminders, thread-snooze, ai/needs-reply.

Reconnect: deltas missed while disconnected are lost; `EngineReads` 'resync' makes the pool rerun every subscription, MessageStore refetches, ThreadCountsStore re-reads `counts.get` on each hello.

Writes. Tasks only: `Actions.queueTask` -> in the main window `EngineBridge._onQueueTask` -> `connection.send(accountId, {type: 'queue-task', task})`; secondary windows tunnel the action to the main window over IPC (`data/action-bridge.ts`). Plus the newer direct RPCs (`draft.create/send/cancelSend`, `events.*`, `contacts.*`, `rules.*`, `account.*`, `ai.*`, `integrations.*`, `settings.*` via the main process).

## 2. DatabaseStore usage, measured

- 71 non-spec files reference `DatabaseStore` (src 61, plugins 10). 79 query call sites (`find` 21, `findAll` 51, `findBy` 11, `modelify` 3, `run` 1, `_query` 1, `count` 0); by area: features/main-calendar 15, data/drafts 10, data/stores 8, data/query 7, features/thread-list 6, features/contacts 4, thread-search 3, plugins/activity 3, the rest 1-2 each.
- Classes queried (call sites): Message 26, Thread 17, Event 12, Contact 6, Calendar 6, Folder 2, Label 2, ContactGroup 2, Task 1, ContactBook 1, plus generic.
- 65 distinct query shapes in the capture test (`SITES` in model-query-capture.test.ts), all of which the engine's `query` already answers except `structuredSearch` (3 call sites: thread-search/query-subscription.ts, thread-search/bar-util.ts, plugins/participant-profile sidebar-related-threads.tsx).
- `.search()` (FTS) 18 sites / 14 files.
- Live queries: `Rx.Observable.fromQuery` 18 sites / 11 files; `new QuerySubscription|MutableQuerySubscription|UnreadQuerySubscription` 10 sites / 6 files; `fromNamedQuerySubscription` 4.
- Plugin API v1 exports 58 modules from data/, mail/ and engine/, among them `DatabaseStore`, `Matcher`, `Attributes`, `Model`, `QuerySubscription`, `MutableQuerySubscription`, `QuerySubscriptionPool`, `QueryResultSet`, `MutableQueryResultSet`, `SearchQueryParser`, `IMAPSearchQueryBackend`, `TaskFactory`, `TaskQueue` (src/packages/api/mailspring-exports.js). Dropping DatabaseStore is a plugin API break (2.0) unless a JSON-only `ModelQuery` facade is kept.

So the engine's one-shot read surface is already complete for the desktop. What's missing is the live part: there's no way to subscribe to a query, so both clients re-implement result maintenance (desktop: Matcher.evaluate + sort-key check + refetch in `QuerySubscription._processChangeRecords`; web: `matchesThreadQuery`/`upsertThreadInPages` in apps/web/src/engine/cache.ts).

Minimum engine additions for a thin client:
- `query.subscribe {query, id}` -> first page + `nextCursor`; notifications `query.changed {id, ops: [{op: insert|update|remove, row, index}] }` or at least `{id, invalidated: true}` with the changed ids; `query.unsubscribe`; `query.setRange` for paging a subscription. The engine knows which rows a commit touched (delta.rs), so it can re-run the subscribed queries whose classes were touched and diff ids.
- A thread-list row that carries what the list renders (participants, snippet, hasAttachment, draft/sending flags, message count without hidden messages) so the per-thread message subscriptions go away.
- `structuredSearch` from the desktop as `search {text, grammar: true}` (engine side done; desktop side is the gap).
- Contact search across accounts with distinct-by-email and the refs/hidden filters (or `contacts.search {accounts}`), plus an engine hook point for `ContactSearchResults` extensions.
- `events.expand` as a subscription (or `query.changed` on Event driving it).

## 4. Duplicated logic

Same thing computed in TS and Rust:
1. Query compilation: `ModelQuery.sql()` + attributes (desktop) vs `model_query.rs` (engine). Kept equal by the parity test; the TS side can go.
2. Live result maintenance: `Matcher.evaluate` + `QuerySubscription._processChangeRecords` (desktop) and `matchesThreadQuery`/`upsertThreadInPages` (web cache.ts) vs the engine's matcher SQL. Three definitions of "does this thread belong in this list".
3. Search grammar: mail/search/parser.ts + ast.ts + backend-local.ts vs `search_grammar.rs` + `search_dates.rs`.
4. Archive/spam/not-spam/trash semantics: `TaskFactory` (desktop), `apps/cli/src/organize.rs`, `apps/mcp/src/tools/write.rs archive_threads`, `airpost-sync/expiration_executor.rs archive_task`, web `features/mailbox/actions.ts`. Five copies.
5. Task JSON construction: desktop data/tasks/*, `crates/airpost-client/src/tasks.rs` (CLI/MCP), web `engine/tasks.ts`.
6. Draft building (quote, signature, participants, subject prefix, mailto, tracking-pixel removal): drafts/factory.ts JS path + message.ts `participantsForReply*` vs airpost-compose (`draft.rs`, `quote.rs`, `participants.rs`, `mailto.rs`, `pixels.rs`).
7. Draft validation: `DraftEditingSession.validateDraftForSending` vs `airpost-compose/validate.rs` (`draft.validate`, which the desktop never calls).
8. Contact parsing and email equivalence: contact.ts `fromString`, ContactStore `parseContactsInString`, utils.ts `emailIsEquivalent` vs airpost-compose/contacts.rs; identity (`Account.me`, `isMe`) vs identity.rs.
9. Thread counts: SQLite `ThreadCounts` fallback vs `counts.get`.
10. Event RSVP: EventRSVPTask (ical.js) vs `events.rsvp` (airpost-pim). ICS parsing in features/events vs airpost-pim/ics.rs.
11. Attachment file naming/layout: `File.safeDisplayName` + `AttachmentStore.pathForFile` vs `airpost-client/files.rs safe_file_name` and the engine's own writer.
12. mbox assembly: mail/mbox.ts vs apps/cli/src/mbox.rs.
13. IMAP UTF-7 / category display names: mail/imap-utf7.ts + Category.displayName (desktop), web `engine/model.ts decodeImapUtf7`/`categoryDisplayName`/`sortCategories`/`ROLE_ORDER`, airpost-client/utf7.rs (CLI `display_name` in organize.rs).
14. Resurfacing message send: window fallback (engine/resurfacing.ts + DraftFactory.createDraftForResurfacing) vs expiration executor.
15. OAuth revocation: oauth-revocation.ts vs `account.remove {revoke}`.
16. Protocol types: engine/protocol.ts (desktop) vs web rpc.ts + types.ts, both hand-written from airpost-ipc.

Same thing computed in desktop and web (TS only):
17. Thread-list query per perspective: MailboxPerspective.threads() vs web hooks.ts `threadListQuery` (comment says "as the desktop's mailbox perspectives build it").
18. Optimistic thread effects of tasks: web `engine/optimistic.ts` re-implements placement rules (Gmail trash/spam drops labels, locked Sent/Drafts) that live in `airpost-store/placement.rs`. The desktop has no optimistic layer; it waits for the engine's local-phase delta.
19. Label hue: `Category.hue()`/`Utils.hueForString` vs web `features/mailbox/labels.ts labelHue` ("the desktop's formula").
20. Delta -> cache application: desktop bridge.ts + QuerySubscriptionPool vs web cache.ts `applyDelta`.
21. Account/connection state derivation: OnlineStatusStore vs web `useProcessState`/`useConnectionProblem`.

## 5. Engine gaps for thin clients (this area)

- Live queries (`query.subscribe` / `query.changed` / `query.unsubscribe`, ranged) — none today; `subscribe` filters by account and class only and ships whole models to every window.
- Thread-list rows with message summaries (kills N+1 per-thread message subscriptions).
- Server-side undo (`task.undo`, undo history) — only undo-send and event `restore` exist; the engine already writes `undoPlacements` for moves.
- Semantic mail actions (`threads.archive|trash|spam|notSpam|move|label|markRead|star`) so TaskFactory and its 4 ports collapse into one.
- Per-task completion notification (or `task.queue {wait}`) so clients don't watch the Task table to run onSuccess/onError.
- Cross-account contact search with distinct-by-email and refs/hidden filters; contact group search; `contacts.delete` and groups (CLI TODO).
- `displayName` (decoded, role-aware) on Folder/Label JSON.
- Engine extension hooks for `prepareNewDraft`, `applyTransformsForSending`, plugin send actions, `ContactSearchResults` (today renderer-only).
- mbox export in the engine.
- Settings the web/mobile would also want but only config.json has: label custom colours. Accounts still have config.json as the desktop's primary copy.
- Sync progress summary (per account) in `engine.status`; send progress for the outbox.
- TS type generation from `crates/airpost-ipc` (not airpost-wire).
- Parsed invitation from `events.expand` with ICS input, so features/events stops using ical.js.

## 6. Surprises

- The engine read path the plan asks for is mostly built: `query` takes `ModelQuery.toJSON()` for all 65 desktop query shapes with a parity test, plus cursor paging and the search grammar. The desktop keeps it behind `core.engine.reads`, default `"sqlite"`, and still sends search to SQLite.
- `crates/airpost-wire` is the backend metadata wire; the engine socket protocol is `crates/airpost-ipc`. Generating TS "from airpost-wire" would generate the wrong thing.
- Many desktop units carry a JS fallback for engines without a feature (`draft-pipeline`, `counts`, `accounts`, `ai-keys`, `expiration-executor`, `rules`, `account-setup`). The desktop bundles its own engine, so these fallbacks (drafts/factory.ts JS path, DraftStore JS send path, ThreadCounts SQL, oauth-revocation.ts, resurfacing window send, keyset key lookup) can be deleted without engine work.
- `EventRSVPTask.forReplying` and `DestroyModelTask` have no callers; `IMAPSearchQueryBackend` is only a plugin export.
- TaskQueue keeps the entire Task table as a live query in every window that loads it.
- The thread list opens one live message subscription per visible thread (plus paging padding of 100), each re-evaluated on every Message delta.
- The renderer opens a raw Unix socket with Node `net` (connection.ts), so the desktop engine client can't be shared with the web as-is; the transport has to be split from the protocol client.
